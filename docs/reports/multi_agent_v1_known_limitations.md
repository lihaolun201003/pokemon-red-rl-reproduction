## 2. Story Agent（对话理解）的限制

1. **对话文本理解不稳定**：真实 OAK 对话被正确读出并记录（证据截图 + 引用原文），
   但模型对“谁在说话/这句话是否主线线索”的判断仍会漂移（同一次运行里对 OAK 的
   称呼出现 “OAK / OAK (likely) / lab NPC” 多种表述）。
2. **结束判定是启发式**：连续 2 次非对话观察或模型 `finish` 才结束；如果模型不断
   按 A 重复打开同一 NPC 的对话，可能一直循环到回合上限（有硬上限，不会无限）。
3. **交互获取是有界确定性探针**：`acquire_dialog` 只按 A + 四个方向，预算 ≤12 次按键。
   需要先打开菜单/使用道具/走位更远的交互它做不到；它拿不到对话时会诚实返回
   `no_dialog`（0 次 API 调用），由 Director 转交 Navigation 继续探索。
4. **重复对话会产生重复任务**：G2 中同一 NPC 的后续对话被提出 3 个措辞近似的
   “再和 OAK 谈谈”任务（描述不同，TaskManager 的 dedupe 只有完全相同描述才合并）。
   这是有意保守（不误删）带来的噪声，后续应在语义层去重。
5. **不保证剧情推进正确**：它不知道剧情路线，只能基于可见文本提出假设/任务；
   “下一步该做什么”可能错误，需要试错与回档兜底。

## 3. Pokémon Agent（战斗）的限制

1. **战斗菜单驱动是确定性执行**：AI 只决定“攻击第几招/逃跑/捕捉/换人/道具”，
   具体按键由像素校验的菜单驱动完成；菜单布局阈值用合成帧 + 真实 text 帧校准，
   真实 mix 界面（换人二段确认、道具列表行几何）仍是近似值，可能按错而回退重观察。
2. **战斗策略朴素**：没有属性表/图鉴知识（设计禁止），只能从可见伤害/血条学习；
   首战可能打得很差甚至失败。这是诚实的能力上限，不是脚本 bug。
3. **战斗 intro/文本需要 A 推进**：真实 Red 的 “Wild X appeared!” 必须按 A 才能
   进入菜单（本轮验收发现并修复）；类似的需要 A 的过场（升级、捕捉提示）仍可能
   让局面暂时“卡在文本”，只能靠有界 settle 预算保护。
4. **捕捉/道具/换人闭环未单独做真实 ROM 验收**：代码路径与记忆结构存在并有单测，
   但本轮真实验收只覆盖了真实野生战斗的决策-执行-结束闭环。
5. **长期培养能力只是结构化占位**：训练/进化/技能学习替换/队伍管理/道具在
   `PokemonMemory` 与接口中建模（`structured_only=True, validated=False`），
   没有真实运行验证。

## 4. Navigation / 探索相关

1. Navigation v2 未被修改；多区域探索仍受其既有行为限制：门口双向传送会来回
   （本轮 G4 中也出现一次 transition 往返），跨区域覆盖不保证完成。
2. 真实战斗/对话结束后必须重新视觉重定位；若重定位失败，Director 会如实记录并
   把任务置为可重试/失败，而不是假定位置未变。重定位偶发失败是已知风险。
3. 大世界的探索仍可能长时间无新发现（G6 证明监测/恢复链路能识别并处理，
   但“最终找到主线”不在本阶段保证范围内）。

## 5. Director / 恢复机制的限制

1. **Director 的 DeepSeek 复盘默认很少触发**：为控制成本，多数验收运行关闭或
   极少调用 `director_review`；其“复杂冲突时的高层协调质量”尚无充分真实数据。
2. **停滞阈值是配置值**：G6 用极小阈值构造可复现场景；长时间真实游戏中
   什么阈值合适仍需调参，过敏感会误回档、过钝会浪费时间。
3. **回档的“学习保留”是悲观标记**：旧分支知识全部标 HISTORICAL，这保证不会把
   历史当事实，但也不会自动把在新分支重新验证过的旧知识“升级”回来（需要后续
   verify 流程），信息利用偏保守。
4. **每分支/总回档上限**会先于“真正解决问题”触发安全暂停：这是成本/循环保护，
   不是失败；但意味着长任务可能需要人工重启/调参。

## 6. 基础设施与工程限制

1. EventBus 是单机单进程实现（内存队列 + JSONL 持久化 + RLock），没有跨进程锁；
   同时运行两个多 Agent 实例会共享同一台账文件/锁文件（入口默认用
   `SingleInstanceLock` 防呆）。
2. 消息投递语义是**至少一次**：消费端按 `message_id` 幂等（Director 持久化
   `processed_messages.json`）；不可逆操作重试前会先重新观察屏幕，但“动作是否已生效”
   在极端崩溃场景下仍可能无法完全判定（设计上选择先观察再决定）。
3. DeepSeek HTTP 连接在极少数情况下会长时间挂起（本轮 1 次，11 分钟无响应）：
   入口/验收用 `api.timeout_s` 收紧 + 外部 watchdog；**库内部仍无全局 watchdog**。
4. `tests/envs` 在本机 `.venv` 缺少 `memory_gym`/`minigrid` 等依赖，pytest 全量
   收集会报 4 个 collection error。这是**预先存在**的环境状况（与本次改动无关），
   本报告与 G0 只用可运行子集，并如实注明。
5. 真实验收截图/存档/审计日志位于 `artifacts/multi_agent_v1/` 与
   `work/multi_agent_v1/`（均已 gitignore），不随仓库发布；ROM/存档/API Key 未提交。
6. 未做长时间（数小时）无人值守运行验收；本阶段目标是“可长期扩展的基础设施”，
   稳定性只验证到本轮运行的时长与预算范围内。
